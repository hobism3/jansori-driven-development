# 초기 입력 부속 설명 — 제품 명세를 덮어쓰지 않음

기준은 새 SPEC.md다. docs/spec-reference.md는 자료 형식 예시일 뿐이다.
이 문서와 테스트셋은 SPEC §6·§7·§8에 따라 **구체적인 수용 기준을 정할 초기 초안**이다.
팀의 실제 승인이나 상세 계약이 이미 확정되었다고 간주하지 않는다.

## 출처와 권한

| 구분 | 내용 |
|---|---|
| 새 SPEC에서 이미 채택 | 내용 불변 버전, 최신 부모/자식과 교정, 정리 시 새 버전, 상태 분리, 비차단 소비, 입구 길이 거부, 보호 변경 승인+최신성 |
| SPEC §8 미정 | 상태 저장·수명, 실제 API/스키마, 헤더/충돌 응답, 상한 숫자, 파일 실패 처리, 구체 Skill 설정, 정리 작업 실패/재시작 |
| 이번 사용자와 합의한 도메인 구성 | 부모 C-model 개발 / 자식 리팩토링·Code Rule, 실제 영상이 있는 C++ 업무 |
| 이번 패키지의 시연 설계 초안 | m_ 기본/boolean is_ 교정, 동일 C 상태 과제, C0/C1/C2 시점, 숫자 영상 연산 |
| 사용자가 제공하지 않은 것 | 실제 사내 코딩 규정, 제품 NR 레지스터/알고리즘, SystemC 타이밍 모델, 실사용 전사 |

spec-reference의 부모 cmodel-rules / 자식 cmodel-naming·interface는 형식 예시다.
이것이 합의한 리팩토링·Code Rule 분류를 폐기하라는 뜻은 아니다.
이번 m_/is_ 사례는 SPEC §7의 설명을 활용한 **시연 선택**이며 실제 사내 정책인 것처럼 쓰지 않는다.

## 개발과 업무 입력의 분리

Jansori Plugin + 로컬 Python 서버가 개발 대상이다.
B의 NR, C의 Local Contrast, 작은 policy CPP는 개발 시작 전에 준비한 업무 입력이다.
서버에 영상 알고리즘이나 사례별 정답 분기를 넣지 않는다.
이 패키지는 mock 서버, adapter, 최적화 정답, 서비스 테스트 구현을 제공하지 않는다.
`tools/verify_sample.py`는 C++ 업무 입력/후보를 검사할 뿐이며 실제 서비스/API를 구현하지 않는다.
입력·기대값을 실제 제품에 연결하는 테스트는 팀의 정상 개발 과정에서 만든다.

## 실행 명령과 산출물의 범위

SPEC §12의 make run, make verify, 범용 make seed가 기준이다.
제품의 자료 복사·후보 검증 자동화 명령 이름은 아직 정하지 않았다.
이번 입력에는 제품과 무관하게 사용할 수 있는 `python3 tools/verify_sample.py`를 제공한다.
이전 입력의 demo-prepare/demo-check 타깃은 새 명세의 확정 계약으로 강제하지 않는다.
필요하면 팀이 설계하되 추가 요구와 검증 영향은 §9에 따라 처리한다.
현재도 사용할 수 있는 일반 shell 복사와 C++ 빌드는 시연 대본에 적었다.

설명용 HTML/PPT는 최소 하나, 영상과 README·이해도 확인은 필수 산출물이다.
영상 비교 도구를 만들어도 그것만으로 문제→교정→다음 결과→기존 규칙 보존의 설명이 끝난 것은 아니다.
5분 이해도 확인은 실제 다른 참가자와 수행한다. 이 문서로 시행을 대신하지 않는다.

## 해석을 확정한 것과 비워 둔 것

자식도 body+corrections를 전달해야 한다는 점은 더 이상 보충 제안이 아니라 I-03 기준선이다.
대상/공유 의도가 명확하면 반영하고, 추론/추가 확인이 필요하면 확인하는 것도 SPEC §3·I-13 기준선이다.
부모·자식 깊이 1단계 제한은 I-15 기준선이다. 저장을 허용한 뒤 조회에서 손자를 생략하는 정책으로 완화하지 않는다.
특정 X-Request-Id 헤더, stale 오류명, compaction_token, 대기 60초, 10,000자, 멱등성 24시간은
새 SPEC이 확정한 값으로 취급하지 않는다. §8 계약이나 설치 환경 확인 결과를 따른다.

## 시연의 공정한 비교

C는 한 종류의 원본 작업물을 세 번 사용한다. C0/C1/C2의 초기 파일과 요청은 동일하다.
C0는 기본 규칙, C1은 교정 후·정리 전, C2는 정리 후다. 각 실행의 실제 ID/version을 기록한다.
C1은 교정 2건으로 임계값 3 미만에서 실행한다. 이후 세 번째 nag는 앞선 규칙 재명시로 의미를 바꾸지 않는다.
이 선택은 빠른 정리 완료를 붙잡기 위한 제품 대기/정지 기능 없이 세 상태를 관찰하기 위한 대본 구성이다.
세 번째 nag가 실제로 의미를 바꿨다면 같은 유효 규칙의 정리 전후 비교라고 주장할 수 없다.
자동 테스트에서는 정리 직전 v4와 직후 v5를 직접 비교해 정확한 내용 경계도 확인한다.

특정 속도 배율은 성공 기준이 아니다. 실제 업무 결과를 바꾸는 주 증거는 교정된 이름과 상태 기능,
기존 일반 멤버·API·영상 계산 보존이며, 이미지·시간은 보조적인 눈에 보이는 업무 증거다.
수치가 맞더라도 실제 Capsule Read와 동일 입력의 비교 없이 교정 효과를 주장하지 않는다.
