# 개발 단계 — 초기 시험 사례를 실제 구현 검증으로 연결

이 문서와 development-cases.json은 개발 전에 제공한다.
서비스 테스트 함수·HTTP 어댑터·mock 서버가 이미 구현되어 있다는 뜻은 아니다.
SPEC §6에 따라 구체적인 수용 기준은 팀이 확정한다. 원본의 불변조건을 완화하지 않는다.

## 처음 한 번 준 자료가 사용되는 흐름

| 개발 활동 | 최초 자료의 사용 |
|---|---|
| 초기 분석 | SPEC/초안/도메인 fixture 구분. CPP를 기존 Jansori 구현으로 취급하지 않음 |
| 요구·사용자 스토리 | A 생성·수락/거절, B 교정, C 세 상태, 길이/장애/정리/확인 분기를 포함 |
| 계획·설계 | §8 결정 순서, 공통 세션 상태와 모든 동작 매핑, 오류/상한 확정 |
| 구현 | 실제 서비스·hook·Skill 처리기와 연결된 테스트 작성. 사례별 case_id/R-ID/I-ID를 추적 |
| Build and Test | make verify로 실제 서버 기동·종료. 전사 필요한 항목은 실제 세션으로 별도 검증 |
| 제출 검토 | README·영상·HTML/PPT·이해도 기록·R/I/F·승인된 축소를 증거와 대조 |

이 표는 AI-DLC의 새 고정 Stage 계획이 아니다. 팀의 설치된 워크플로우에 위 입력을 처음부터 반영한다.
중간에 사용자가 adapter나 테스트 코드의 삽입 시점을 다시 지시하는 구조로 만들지 않는다.

## JSON 사례 읽는 법

46개 사례에 case_id, r_ids, invariants, mode, setup, actions, expected, evidence,
decision_dependencies가 있다. 이 필드는 **수용 테스트 자료 형식**이며 제품 API 스키마가 아니다.
`D-xx`가 있으면 contract-decisions.md와 §8 결정 뒤 실제 값/함수/오류 계약으로 매핑한다.
입력·기대값 초안을 수용 기준으로 확정할 때 관련 SPEC 조항과 근거를 유지한다.

자동: 실제 파일/JSON/version/내용/시간 상한/경로/요청 원자성.
전사: 모델 선택·명확성 판단·저장 제안·실제 동의·유효 지침 의미 보존·업무 적용.
복합 사례는 자동 부분과 전사 부분을 따로 보고한다. 전사 대상에 기계적 보조 검사가 있더라도
그 검사만으로 사람/Claude 의미 판단 전체가 검증된 것은 아니다.

## 검증 대상과 테스트 대역

make verify는 팀의 실제 서버를 테스트 안에서 시작/종료해야 한다. 자격증명 없이 기계적 계약을 검사한다.
새로운 별도 fake Store만 만든 뒤 그것을 통과시킨 결과는 제품 검증이 아니다.
가상시계, 네트워크 오류, 파일 쓰기 실패, LLM 응답 경계의 대역은 허용하되 범위를 표시한다.
LLM 정리 결과를 직접 넣은 자동 검사는 토큰/버전/원자성 연결만 확인하며 의미 보존은 실제 전사로 확인한다.
설명 이해도 기록은 자동으로 채울 수 없다.

## 사전 업무 코드와 기대값

B의 NR과 C의 free function DoProcess는 기존 영상 수치 계약을 만족한다.
C의 LocalContrastModel 관리 상태는 의도적으로 미완성이며 C가 구현하는 과제다.
`workload-golden.json`: 영상 42사례의 B/C 기대값과 오류 5조건. 기존 36사례를 유지하고 부호 있는 분수 나눗셈 사례 6개를 추가했다.
`lifecycle-golden.json`: C의 공개 관측 24단계. 반환 영상, 비기본 파라미터 Reset 보존, 객체 두 개의 교차 실행/Reset과 실패 상태 보존을 포함한다.
`three-state-golden.json`: 평가자 전용 private 멤버명/상태·version 기대값.

원본과 기대값을 고쳐 테스트를 통과시키지 않는다. 수정할 후보는 별도 작업 공간의 복사본이다.
원본 starter가 상태 기능을 만족하지 않는 것은 제공 자료 결함이 아니라 시연 과제의 출발점이다.
정답 C++나 정답이 포함된 golden/TASK를 C에게 전달하지 않는다.

## 이미 제공한 샘플 평가기

`tools/verify_sample.py`는 표준 Python과 C++17 컴파일러로 입력/후보를 검사한다.
사용법과 exit code는 `docs/sample-verification.md`를 따른다. 서비스 테스트 어댑터가 아니다.
C의 수치 검사는 free DoProcess와 클래스 DoRun을 각각 같은 수치 golden과 비교한다.
최종 판정은 평가자 보관 runner/probe/API 헤더로 수행하고, 후보가 수정한 관측기에 의존하지 않는다.
이 검사를 통과해도 private 선언·Capsule Read·실제 잔소리 전달의 전사 검증은 남는다.

## 결과 기록

자동: case_id → R/I → 확정 계약 → 실제 테스트 위치 → 기대/실제 → 판정.
전사: 세션·요청·실제 로드 ID/version·파일 Read·대상·공유·동의·작업·기대/실제.
미실행=NOT RUN, 기능 없음=미구현, 관측 불일치=실패, 사람 승인 축소=승인된 제외.
DOCS를 작성한 것만으로 SPEC §11 실패 조건이 해소되지 않는다.
